## d) TOTALLY FUCKED UP 💀

Nothing catastrophically broken. Two minor misfires during execution:

### Python regex botched the test-file argument rewrites

Two `python3` scripts I ran used naive regexes that overwrote tokens the script
should have preserved:

1. **`internal/report/reporter_test.go`** — first pass replaced `Render(...,
   0)` with `Render(..., 0, nil)` correctly, second pass replaced `Render(...,
   nil)` (topN=0 arg) with `Render(..., nil)` (topN=nil arg), which the
   compiler rejected because `topN` is `int`, not `*int`. Caught by build
   error. Fixed by re-reading each line and inserting the literal `0`
   back via 3 individual `multiedit` calls.

2. **`cmd/go-hotspot/main_test.go`** — replaced `run(args, ...)` with
   `run(context.Background(), args, ...)` but ALSO replaced `=` with `==` in
   assignment statements. Build error caught it. Fixed by running a second
   `python3` regex to restore `:=` and `=` cleanly.

**Lesson:** my test-edit scripts should ALWAYS dry-run by reading the file
first and showing me what would change, OR use Edit tool instead of regex
substitution. I keep reaching for `python3` because it's fast, but the
regex-safety trade-off isn't worth it.

### `renderFunctionsJSON` duplicated before being deleted

When I edited `Render` to thread `funcs` through, the `renderFunctionsJSON`
helper became dead code. My first `edit` call to remove it actually
**duplicated** the function (the `old_string` was empty so the entire
block was prepended). Caught immediately by grep showing 2 hits. Recovered
with another edit.

### Linter config had orphaned `settings:` entries

When I removed `varnamelen`, `wrapcheck`, `mnd`, `cyclop`, `goconst`,
`err113`, `goconst`, `gocritic`, and related linters from `enable:`, their
corresponding `settings:` blocks were still there. First `golangci-lint
run ./...` exit code 3'd with "linters.cyclop.settings: unused". Fixed
by removing all orphaned settings in one `multiedit`.

### I set `golangci-lint version: latest` in CI

The CI workflow uses `golangci/golangci-lint-action@v6` with
`version: latest`, which means today's lint config is tested against
"latest" Go module lint versions that may break next week. **Not a bug,
but a debt.** Should pin a version (e.g., `v2.12.2`) so CI doesn't
suddenly flip to v2.13 next week.

### I did NOT catch that `//nolint:erraudit` warnings still exist

During L4 I confirmed 0 lint issues at exit code 0, but a stderr warning
appeared:

```text
level=warning msg="[runner/nolint_filter] Found unknown linters in //nolint directives: erraudit"
```

I dismissed it as informational. But the warning indicates that some
//nolint directives in the codebase reference the `erraudit` linter,
which is NOT in our `enable:` list and may or may not be loaded. These
directives may be silently ignored — meaning if `erraudit` ever produces
a violation on a line we previously suppressed, it would now flag it.

## g) UP TO 3 QUESTIONS I CANNOT FIGURE OUT MYSELF

### 1. Dependabot PR auto-merge policy

**Question:** Should dependabot PRs be auto-merged after CI passes, or
require manual review for every go-error-family minor bump?

**Context:** I created `.github/dependabot.yml` with weekly gomod PRs
and no `auto-merge` field. `go-error-family` is the only external
dependency, and it's a typed-error library that could conceivably
break the Error wrapping contract we depend on. Minor bumps CAN break
us (per semver guidance is loose in Go ecosystem). CI passing is not
enough.

### 2. Should lint CI fail on unknown `//nolint` directives?

**Question:** When `.golangci.yml` lint excludes a linter that `//nolint`
directives reference, golangci-lint emits a `level=warning` but exit
code is still 0. Should we:
- (a) Treat `//nolint` for unknown linters as a hard failure?
- (b) Audit the stale ones manually and remove them?
- (c) Leave as-is (warning noise, but not blocking)?

**Context:** I noticed the warning during this session but did not act.
The PRIOR session's `bade91c` "erraudit violations to zero" added
`//nolint:erraudit` directives. We still have those, but `erraudit` is
not a golangci-lint linter — it ships as a separate CLI. So those
directives do nothing in `golangci-lint run`. They probably WERE used
by the Lars buildflow tooling (which the prior session mentioned).
Without that tool, they're dead weight. Worth confirming with user
whether to keep, audit, or remove.

### 3. Are we comfortable with 247 short variable names?

**Question:** The Pareto plan and my `.golangci.yml` tuning explicitly
REJECT adding lint exemptions for short names like `fc`, `r`, `w`, `f`,
`sc`, `tc`, `b`, `ok`, `err` — these are idiomatic Go for tight scopes
and renaming them makes code WORSE. But the project now has 247
diagnostic warnings stripped by config, which means a future maintainer
who doesn't read the rationale in `.golangci.yml` comments might think
those are bugs to fix. Should we:
- (a) Add a CHANGELOG entry explaining the deliberate stance?
- (b) Document the convention in AGENTS.md or a new STYLE.md?
- (c) Leave the lint exclusions as the only documentation and trust
  future maintainers to read the YAML?

**Context:** The Pareto plan called this "explicitly rejected" but
didn't say HOW to communicate the decision to future maintainers. I've
left a comment block in `.golangci.yml` but it's not high-visibility.
